# ADR-0013: The migration runner applies the estate's generated migration

**Status:** Accepted
**Date:** 2026-09-13
**Deciders:** Architecture
**Supersedes:** ADR-0005 (DbUp for schema migrations)
**Relates to:** ADR-0011 (packs check the schema fingerprint), L2-R2 `db/MIGRATION-RUNBOOK.md`,
L2-R2 `build/generate-state-migration.py`

---

## Context

ADR-0005 chose DbUp — embedded, versioned SQL scripts applied in order with a journal table.
That was decided on 2025-11-01, before the L2-R2 estate settled its own schema authority. Since
then the estate has one: `db/stable_baseline_ddl.sql` is generated by
`build/generate-baseline-ddl.py`, verified by `build/verify-baseline-ddl.py`, and a state moves
to it by a migration that `build/generate-state-migration.py` **emits** from the difference
between the state's capture and the baseline — with an aborting data check before every
narrowing ALTER, because "MySQL stops at the first error and does NOT roll back DDL".

A DbUp script corpus inside the installer would be a **second source of schema truth**. Two
authorities disagree within a sprint, and the failure mode is a node whose schema neither the
verifier nor the fingerprinter recognises. `tasks.md` 17.5 was therefore left open on
2026-08-29 with the note that this ADR had to exist before the runner did.

## Decision

**The installer does not own migrations. It applies the estate's.**

- A release medium carries, for each `(from_schema_version, to_schema_version)` pair inside the
  manifest's declared upgrade window, the migration SQL that `build/generate-state-migration.py`
  emitted for that pair, plus the `preflight_checks.sql` / `postcheck.sql` that
  `db/MIGRATION-RUNBOOK.md` already prescribes. They are payloads, hashed and signed like
  everything else on the medium.
- `UpgradeEngine` runs, in order: fingerprint the live schema (`MySqlSchemaFingerprinter`) →
  refuse if the fingerprint is not the one the migration was generated *from* (a node that
  drifted is repaired by the drift report, not migrated over) → the pre-upgrade backup (already
  built) → preflight checks → the migration, statement by statement, stopping at the first
  error exactly as the runbook says → postcheck → fingerprint again → refuse unless the result
  is the fingerprint the medium was cut *to* → the table census, which must equal the baseline's
  count for that version.
- The journal is the estate's: the fingerprint before and after, the migration file's hash, and
  the counts go into the node's `AuditChain`, not a DbUp `SchemaVersions` table.
- A migration that the abort-first checks stop is a **refusal with the offending row named**, the
  same as a state cutover, and the safety backup is named in the message. The operator's next
  step is the drift report and the narrowing ledger (`db/narrowing-candidates.txt`), which is
  the same next step a DBA has on a state cutover.

## Consequences

- One schema authority, on the node as in the estate. The verifier, the fingerprinter, the
  narrowing ledger and the installer all speak the same `live-*` vocabulary.
- The installer's upgrade correctness is exactly the estate's migration correctness — no
  better, no worse, and tested by the same tooling.
- The medium grows by the migration files for the window it declares (tens of KB to a few MB
  each; a full `<State>_to_baseline.sql` is ~3.4 MB, and node-to-node steps are far smaller).
- **Superseded:** ADR-0005's DbUp dependency is removed from `Directory.Packages.props`; no
  DbUp journal table is created; `tasks.md` 17.5 is now buildable.
